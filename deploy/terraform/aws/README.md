# Wiggle on AWS — EKS + Aurora PostgreSQL (Terraform)

Stands up a production-shaped Wiggle control plane on AWS:

- a **VPC** (public + private subnets across N AZs, one NAT gateway),
- an **EKS** cluster with a managed node group,
- an **Aurora PostgreSQL** cluster (writer + readers) reachable only from the EKS nodes, and
- the **Wiggle Helm chart** ([`deploy/helm/wiggle`](../../helm/wiggle)) deployed against Aurora — several
  server nodes that **cluster on the shared database** (the HA "cluster on one DB" posture; no
  coordinator).

The Wiggle image is the signed, non-root, distroless one; the pod runs hardened by default (read-only
root fs, all caps dropped) straight from the chart.

## Prerequisites

- Terraform >= 1.6, the **AWS CLI** (used by the `aws eks get-token` auth exec), and `kubectl`.
- AWS credentials with permission to create VPC/EKS/RDS/IAM (e.g. `export AWS_PROFILE=…`).

## Use

```bash
cp terraform.tfvars.example terraform.tfvars   # optional — every var has a default
terraform init
terraform apply
```

> **First apply:** the `kubernetes`/`helm` providers authenticate to a cluster that doesn't exist yet,
> which Terraform can't fully resolve during the very first plan. If apply errors on the Kubernetes
> resources, stage the cluster first, then re-run:
> ```bash
> terraform apply -target=module.eks -target=module.aurora
> terraform apply
> ```

Then point `kubectl` at it (the command is an output):

```bash
$(terraform output -raw kubeconfig_command)
kubectl -n wiggle get pods
```

Reach the gRPC control plane from your machine:

```bash
kubectl -n wiggle port-forward svc/wiggle 8080:8080
# workers/clients now connect to localhost:8080
```

## What you get

| Output | Meaning |
|---|---|
| `cluster_name` | the EKS cluster |
| `kubeconfig_command` | `aws eks update-kubeconfig …` |
| `aurora_endpoint` | Aurora writer endpoint (the JDBC host) |
| `wiggle_service` | in-cluster gRPC address (`wiggle.wiggle.svc:8080`) |
| `database_password_secret` | the k8s Secret holding the JDBC credentials |

The database password is generated by Terraform, stored in a Kubernetes Secret (keys `url`/`user`/
`password`, consumed by the chart's `storage.jdbc.existingSecret`), and kept in Terraform state — use
an **encrypted remote backend** (S3 + DynamoDB lock) for anything real.

## Cost & hardening notes

- Defaults (3× `m6i.large` nodes, 2× `db.r6g.large` Aurora, one NAT gateway) are production-ish, not
  free-tier. Shrink `node_*` / `aurora_*` for a trial.
- Set `cluster_public_access = false` and reach the EKS API over a bastion/VPN for production.
- `single_nat_gateway = true` (in `vpc.tf`) trades per-AZ NAT HA for cost — flip it for production.
- `skip_final_snapshot = true` on Aurora is convenient for demos; disable it where data matters.
